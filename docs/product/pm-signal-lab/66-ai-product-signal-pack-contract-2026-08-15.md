# AI Product Signal Pack Contract

Date: 2026-08-15
Surface: PM Signal Lab deterministic sample workflow, domain labels, README, and design documentation
Audience: international PMs, AI PMs, founders, product designers, and product engineers
Locale: English-first `en-US`

## Decision

Reframe the deterministic sample pack around a concrete AI product review:
an AI support copilot whose draft answers, source freshness, evaluation
coverage, and downstream resolution must be reviewed by a person. The product
will show the domain through real evidence objects and limits, not through a
chat interface, model-thinking animation, confidence theatre, or a provider
claim.

This is a product-truth and visual-quality change at the same time. The first
run quote, loaded source rows, candidate claims, and smallest experiment will
now make the AI PM job legible within the existing field-sheet composition.
The workbench should feel more like an evaluation desk than a generic AI
workspace.

## Product Craft Contract

### Problem frame

- **User/job:** an AI PM or product operator needs to separate a user's source
  line, an assistant behavior observation, an evaluation gap, and the next
  experiment before treating a polished draft as a product outcome.
- **Current friction:** the current fixture is a sound PM workflow but its
  generic signals do not make the AI PM portfolio angle visible. A visitor can
  see a workbench without seeing the specific AI product judgment being
  practiced.
- **Desired outcome:** the first sample line and the loaded workbench make it
  obvious that this is about reviewing an AI support copilot while preserving
  the same source-first, no-magic interaction model.
- **Evidence available:** 1,042-repository reference study, current local and
  hosted UI evidence, existing deterministic domain engine, and the current
  English-first product boundary.
- **Not yet known:** whether international PMs prefer this scenario to other AI
  PM jobs, whether they would bring their own evaluation pack, and whether it
  changes GitHub discovery or stars. Those require external evidence.

### Subject specificity

The sample pack uses these domain objects:

- assistant draft, source freshness, missing-source case, evaluation review,
  refusal/review path, copied response, and resolved support case;
- source folio, claim status, limitation, primary metric, guardrail, smallest
  test, and decision rule;
- `Evaluation review` is a visible evidence type. The underlying identifier is
  `evaluation` and remains provider-neutral.

The pack is explicitly a fictional local fixture. It does not represent a
live support queue, benchmark result, model score, customer record, or user
study.

### Composition brief

- **First read:** the source line someone said about the assistant draft.
- **Second read:** the source type, freshness/coverage limitation, and whether
  the line is evidence or only a design hypothesis.
- **Primary action:** open the sample worksheet, then start source review.
- **Content relationship:** `Source → Claim → Smallest test`.
- **Density:** medium on first run, medium-high after loading; domain nouns add
  information but no new panels.
- **Alignment spine:** workflow rail → source folio → claim mapping → test
  brief.
- **Layout archetype:** single-sheet evidence ledger with an annotated
  workpaper and a quiet context note.
- **Responsive reflow:** preserve the same sequence on mobile; do not add a
  second AI explanation block to compensate for the narrow viewport.
- **What not to use:** chat bubbles, model avatars, confidence meters,
  hallucinated activity feeds, gradients, glass, or repeated rounded cards.

### Creative directions considered

1. **AI assistant demo:** show a generated answer and let the visitor accept it.
   Rejected because it would create provider ambiguity and overtrust.
2. **Evaluation desk:** show source, freshness, test coverage, uncertainty,
   and human review in a real PM worksheet. Selected because it demonstrates AI
   product judgment while keeping the user in control.
3. **Generic PM template:** keep the current scenario broad. Rejected because
   it hides the portfolio wedge and makes the product easier to confuse with a
   notes template.

### No-AI-feel guard

- The AI subject appears in the evidence and claim objects, not in a fake
  assistant persona.
- The fixture says what is missing: no live model, no real support outcome, no
  benchmark, and no adoption evidence.
- The words `copy`, `draft`, `source`, `freshness`, `review`, and `resolution`
  describe observable product work; `intelligent`, `seamless`, `powerful`, and
  `revolutionary` stay out.
- The layout remains rows, folios, dividers, and one action. No new visual
  container is added only to make the product look more AI-native.

### UX state model

| State | Required behavior |
|---|---|
| First-time | Show a concrete AI support-copilot source line and one sample action. |
| Loading | Say the local worksheet is opening; do not imply a model is running. |
| Loaded | Show interview, support, product observation, and evaluation-review rows with dates and source identity. |
| Verify | Keep `Source-backed`, `Needs your review`, and `Missing evidence` visible. |
| Decide | Keep primary metric, guardrail, smallest test, and decision rule editable. |
| Error | Preserve the current workspace and offer a safe recovery. |
| Mobile | Keep the top stepper, source line, and sticky action reachable at 390px. |
| Accessibility | Preserve semantic type labels, focus, keyboard routing, and readable status text. Native screen-reader output remains not covered without direct execution. |
| Trust | State that the sample is local and deterministic, and that copying a response is not proof of resolution. |

## Product Messaging Contract

### Message Job

- **Decision:** should a reviewer treat an assistant draft as a usable product
  outcome or as a source-linked hypothesis that still needs a test?
- **User job:** inspect one AI product signal and define the smallest next test.
- **Target action:** open the sample, expand a source, review a claim, and draft
  the experiment.
- **Success metric:** task comprehension and completion in five-minute sessions;
  current non-owner evidence is `Not provided`.

### Source Truth

- **Product truth:** the demo derives deterministic claims from four local demo
  signals and requires a human review action before export.
- **Proof:** visible source rows, source mapping, limitation text, deterministic
  domain tests, current screenshots, hosted verifier, and browser traces.
- **Boundary:** no external model provider, score, production support case,
  benchmark, adoption, traffic, or GitHub star result is represented as proven.

### Positioning

- **Category:** local-first AI product evidence worksheet.
- **Alternative:** a chat transcript, copied assistant answer, or notes page
  that separates the draft from its source and outcome.
- **Differentiated mechanism:** preserve the source and limitation beside each
  claim, then turn the remaining uncertainty into a test with a guardrail.
- **Not for:** live model evaluation, automatic support decisions, or replacing
  human review.

### Copy Architecture and no-AI copy guard

- Lead with the literal sample object, not an AI promise.
- Keep each source row anchored to one line, one identity, one date, and one
  limitation.
- Use `Evaluation review` rather than an abstract `Expert` label for the sample
  type, while retaining the provider-neutral domain identifier.
- Do not call a copied answer a resolution, a fixture a benchmark, or a
  proposed threshold a research result.
- Keep sentence rhythm uneven and concrete; do not add a summary slogan after
  the source workbench.

### Channel learning

- **Hypothesis:** a concrete AI support-copilot fixture will help an
  international PM understand the portfolio wedge faster than a generic signal
  pack.
- **Primary metric:** whether a non-owner tester can name one source-backed or
  still-open claim and one next test.
- **Guardrails:** no increase in trust confusion, no implied model quality, no
  raw private evidence in the public feedback path, and no star-oriented CTA.
- **Writeback:** record actual tester reports in the public pilot issue or a
  de-identified local note; do not infer from page views or stars.

## Acceptance criteria

| ID | Criterion | Observable oracle |
|---|---|---|
| AC-1 | The sample is AI PM-specific without pretending to be a model | First-run sample and loaded pack contain `AI support copilot`, `Evaluation review`, source/freshness or coverage limits, and no provider/activity claim. |

| AC-3 | Claims preserve uncertainty | The deterministic set includes a supported source-linked direction, a review-needed design hypothesis, and a missing-evidence outcome claim. |

| AC-6 | English-first public surfaces align | README, `DESIGN.md`, current verifier strings, and the hosted UI describe the same sample scenario; historical audits remain historical. |
| AC-7 | Existing user paths remain safe | Tests, typecheck, build, diff check, first-run/loaded/mobile screenshots, source expansion, review, experiment, export, and hosted HTTP verification pass at their evidence layers. |

## Release and evidence gate

Hold the release if the fixture looks like a provider demo, if evaluation
coverage is not visible, if the missing outcome claim becomes supported without
new evidence, if the source rows lose hierarchy, or if the hosted verifier
fails. A green build is necessary but not sufficient.

Required evidence after implementation:

- local test/type/build/diff results;
- fresh first-run and loaded screenshots at 1280×900 and 390×844;
- browser trace for sample load, source expansion, review, experiment, export,
  and mobile overflow;
- canonical HTTP and hashed-asset verification after deployment;
- explicit `Not covered` list for Chrome Extension availability, native
  assistive technology, physical touch, non-owner PM sessions, provider/model
  quality, adoption, and stars.

## Risk, fallback, and rollback

| Risk | Detection | Fallback / rollback |
|---|---|---|
| The scenario sounds like a fabricated customer study | Review source labels, copy, and README boundary | Use `fictional local fixture` / `demo signal` wording and remove any implied production result. |
| AI-specific nouns make the screen feel like a chatbot | Screenshot and box/layout review | Keep rows and folios; remove any added AI badge, avatar, chat surface, or activity wording. |
| `evaluation` breaks existing custom-signal behavior | Typecheck, tests, form option smoke | Keep `expert` as a backward-compatible option if needed and preserve unknown-input rejection at the type boundary. |
| Generic synthesis text survives in the bundle | Forbidden-string scan and hosted verifier | Update the current source and verifier together before merge. |
| A visual or behavioral regression appears | Local and hosted browser matrix | Hold merge; revert the single branch commit. No persisted data or migration is involved. |

## UX / AI / security gate

- **UX:** first-time, empty, loading, error, recovery, backtracking, mobile,
  keyboard, and trust states remain in scope.
- **AI:** no provider call, model score, fake progress, chain-of-thought,
  automatic decision, or unsupported quality claim enters the diff.
- **Security/privacy:** fixture content is fictional; custom content remains
  on the page; no secrets, telemetry, GitHub mutation, or automatic feedback
  submission is added.
- **Public trust:** the README and UI state that the sample is deterministic and
  that copied output is not proof of resolution.

## Not covered

- Native VoiceOver, NVDA, TalkBack, rotor output, or a screen-reader usability
  session.
- Physical-device touch, share sheet, download behavior on every browser, and
  hardware keyboard behavior.
- Real support tickets, live model output, model quality, benchmark validity,
  production resolution, or customer adoption.
- Five external PM sessions, retention, conversion, traffic, GitHub stars, or
  the 10,000-star outcome.
