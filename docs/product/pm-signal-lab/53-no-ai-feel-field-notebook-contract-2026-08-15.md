## Product Craft Contract

### Product Truth

- **Target user:** International PM-adjacent practitioners evaluating a real product signal.
- **Job:** Keep the original line attached while deciding what it can support and what test is small enough to run.
- **First read:** “This is a source-backed PM worksheet; I can load a sample or add one signal now.”
- **Proof:** The visible sample source excerpt, source identity, evidence type, limitation language, deterministic claim review, and exportable decision brief.
- **Success:** A user can complete one reviewable source → claim → smallest-test path without believing that the system validated adoption or made a decision for them.

### Subject Specificity

- **Domain objects:** source line, evidence type, folio, claim, limitation, smallest test, guardrail, decision rule, field note, `Not covered`.
- **User language:** “What did the user actually say?”, “What does this line support?”, “What would change the next move?”
- **Real constraints:** local-only state, refresh reset, no external provider, manual review, missing evidence, and no automatic submission.
- **Signature detail:** a restrained evidence spine with folio marks and one rust signal line; it is structural provenance, not decoration.

### Creative Direction

- **Selected:** `Field notebook / decision instrument` — cool mineral paper, graphite text, rust for the next action, teal for source/trust, ruled rows, one strong folio mark.
- **Accepted:** Pillow Fit's low-anxiety tool discipline; Altoslab's professional restraint; the existing source spine because it maps to product truth.
- **Rejected:** generic AI gradient hero, floating orb, card-soup dashboard, glass surfaces, fake model activity, and a dark technical SaaS skin that would make a source-review task feel like infrastructure.

### Composition Brief

- **First read:** literal product job and one visible next action.
- **Second read:** the sample source line, source identity, and the sentence explaining what remains unproven.
- **Primary action:** `Load sample data` on empty; `Start review` after the sample is loaded.
- **Content relationship:** a working paper: source line → claim → smallest test; use ruled sections and list rows before containerized cards.
- **Density:** medium on first run, medium-high once loaded.
- **Alignment spine:** topbar → workbench title → source ledger; the context rail follows the same vertical rule.
- **Responsive reflow:** single-column mobile; stepper remains visible; source excerpt and next action remain before secondary boundary copy; sticky action stays readable.
- **Do not use:** decorative gradients, large empty hero art, repeated rounded panels, ambiguous “AI-powered” claims, or copy that implies validation.

### No-AI-Feel Guard

- Keep the actual source and evidence vocabulary in the first viewport.
- Prefer a ruled section, list row, divider, or definition list over a new card.
- Use one brand accent only where it means “next action” or “signal.”
- Keep the human decision owner and the local boundary near the action.
- Do not add fake progress, typing, confidence scores, or model activity.

### UX State Model

- **First-time / empty:** show the literal job, one real sample line, `Load sample data`, and `Add your own signal`.
- **Loading:** show a short honest loading state; no simulated reasoning.
- **Loaded:** show source rows, counts as working-set context, and a review docket.
- **Error:** preserve the workspace and give a recovery action.
- **Recovery:** reset, edit, keep as hypothesis, mark missing, or return to the previous step.
- **Mobile:** no horizontal overflow; primary action remains reachable; labels and long English copy wrap.
- **Accessibility:** visible labels, semantic landmarks, focus ring, keyboard path, status announcements, reduced motion, and native screen-reader boundary explicitly recorded.
- **Trust:** local-only copy, source/limitation visibility, human approval, manual handoff, and `Not covered` remain visible.

### User-facing UX gate

The user-facing UX gate covers first-time, empty, loading, error, recovery, mobile, accessibility, and trust states. No visual polish is accepted if it hides a state or weakens the manual decision boundary.
